# HeishaMon NR update tab

An importable Node-RED tab for [HeishaMoNR](https://github.com/edterbak/HeishaMoNR) that reduces every package update to a few dashboard clicks: **Check for updates**, **Back up settings**, **Restore backup**, **Update flow**, plus **Download flows** for a full flow export. No scripts, no SSH: the tab talks to Node-RED's own Admin API from inside the flow, and follows the in-flow Admin API precedent that the flow already sets (the GUI_01/GUI_02 tab-toggle uses `PUT /flow/:id`).

- Flow file: [`update-tab.json`](update-tab.json), v4.12.10, 100 nodes (one flow tab with its own `ui_tab` and two `ui_group` columns; all node ids prefixed `wpu`, so an import never collides with package ids).
- Verified against the real 26.3.1 and 26.5.1 packages: 127/127 automated checks green on v4.7; v4.8 (security fixes, see [CHANGELOG.md](CHANGELOG.md)) re-validated structurally; v4.8.1 re-ran the harness after a source-verified review: 91/91; ## Why

The current update procedure (manual tab deletion, config cleanup, screenshots for settings) is error-prone and costs every user 30+ minutes per release. Since node ids are already stable across releases (verified: 26.3.1 -> 26.5.1 share 3547 ids; 1 removed, 15 added), a scripted atomic update is safe. This tab ships inside the flow package and reduces every future update to the four steps above. Admin credentials can come from environment variables instead of the dashboard fields, so no password needs to sit in the editor or context.

## What's in it

- **Check for updates** (v4.12.6: one button checks both): for the flow it fetches the running flows via the Admin API, reads the version from the "Line - Changelog" node, compares against `version.json` in the repo and shows Installed vs Available. If `version.json` is missing, it automatically falls back to a repo scan: the plain GitHub repo page is read, the highest "flows (X stable).json" picked and the raw URL built (no GitHub API, so no rate limits). Verified live against the repo page; the built raw URL serves the real 2.9 MB flow (HTTP 200). Since v4.7, network-level failures (DNS/connection errors, which carry no status code) surface immediately as a readable dashboard error instead of disappearing silently. On the same click, the **Tab status** field refreshes against this repo's pinned `version.json` (merged check: one Admin API call, then two cache-busted raw fetches in parallel, so one button now answers both "is the flow current?" and "is the tab current?").
- **Back up settings**: dumps the full global context (F_RTC, F_CCC, F_SS and all history) to two files in the Node-RED data directory: a timestamped archive and a fixed `wp-backup-latest.json`; downloadable via `/wpupdate/backup` (clickable relative link in the private toast, same host as the dashboard), only with the one-time download token from a **private** toast (visible only to the client that clicked Back up, `sendall: false` + `socketid`, link is a raw anchor since v4.10.1) and stays open for **60 seconds** (v4.12.7, with a bold click-here-to-download line: a DB1 toast has no sticky mode, displayTime 0 falls back to the default per the 3.6.3 ui_toast.js source, so the node displayTime is empty and the message sets timeout=60), valid for 24 hours (http nodes sit outside adminAuth). The tab's own `WPU_` state is excluded, so backups never nest themselves. An optional **Backup folder** field supports a fixed path (in a Docker container: `/data`).
- **Download flows** (v4.10): fetches the complete running flow via the Admin API (`GET /flows`) and serves it at `/wpupdate/flows` — same protection model as the backup endpoint: a fresh one-time token per click, shown only in a private toast to the clicking client (`sendall: false` + `msg.socketid`), valid 24 hours; 404 before the first click, 403 without/wrong/expired token. The dump lives only in the memory store. Note: the Admin API strips credential-store secrets from `GET /flows` (verified live on Node-RED 5.0.10 — a config node with `credentials: {user, pass}` comes back without them), but any legacy plaintext fields in node configs are included — which is exactly why the endpoint stays token-gated. Since v4.12 the two `http response` nodes carry `headers: {}` (empty object, not `[]`), so the `Content-Disposition: attachment` set by the serve functions is actually sent on Node-RED 5.x and the toast link downloads the file onto the browsing device instead of rendering it (verified live on Node-RED 5.0.10). Since v4.12.7 this download toast also stays open 60 seconds (same mechanism as the backup toast).
- **Dashboard layout** (v4.12, v4.12.6): the tab renders as exactly **two half-screen columns**, with a strict flow-vs-tab vocabulary. Column 1, **Update**: an Ed-style divider captioned "Flow", then [Check for updates] (flow + tab in one click), [Update flow], Installed + Available on one row, the **Flow status** field, then a divider captioned "This tab" with [Update tab] and the **Tab status** field. Column 2, **Backup & Admin**: a divider captioned "Backup", then [Back up settings], [Restore backup], [Confirm restore backup], [Download flows], Backup folder, then a divider captioned "Admin" with the User and Password inputs. Since v4.12.9 every block has a Title-Case caption and both status fields share one widget style and sentence format. Exactly two `ui_group`s of width 6: node-red-dashboard places at most these two side by side, so the tab is always two columns on a wide screen (v4.12.2's four separate sections all ended up in one row on a wide browser) and one column on narrow screens. Every button fills a full 6-unit row, so labels never truncate (a width-3 button renders ellipsized text such as "CHECK UPDATER VER" on the live dashboard).
- **Update tab** (v4.11, v4.12.6 check-then-apply in one button): self-update of this tab from this repo. Safe to press any time: it fetches the pinned `version.json` (`raw.githubusercontent.com/MikeyMan83/HeishamonNR-update-tab/main/version.json`), compares it with the `version` field on the tab node and shows a full sentence in the **Tab status** field: "Tab update available: x.y.z. Press [Update tab]." (plus " (current version unknown)" when no running marker survives); on "Up to date (x.y.z)." nothing changes. When newer it downloads `update-tab.json` with the flowUrl **allowlisted to this repo**, and validates (JSON array, every id `wpu`-prefixed, unique ids, contains `wpu-tab-0001`, tab version must match version.json), runs the palette pre-flight, replaces **only the `wpu*` nodes** and deploys atomically (`POST /flows`, rev, full) with a pre-update snapshot first. Merge stats (new/updated/removed/unchanged) in the Node-RED log, summary in the deploy toast ("Tab update succeeded" vs "Flow update succeeded"; the POST is tagged with its phase). Since v4.12.4 a boot inject refreshes the field on every flow start (since v4.12.9 the sentence "Running tab version <version>."), so the field never lingers on a stale "(update!)" after a restart or self-update. First install is still a manual import; afterwards the tab keeps itself current. Rollback: re-import an older `update-tab.json` from this repo's git history (or the `wp-preupdate-flows-*` snapshot). Trust note: the pinned repo ships executable flow code, so protect the repo/branch (the merge itself is wpu-only and cannot touch anything else).
- **Error reporting**: every failure class (network, HTTP statuses, admin login, validation refusals, deploy 409/failed POST) shows a toast (5 s, top-right), keeps the last message in the persistent **Status** field on the tab, and leaves a `[WP Update]` warn line in the Node-RED container log; deploys log an OK line plus full merge stats and NEW/UPDATED/REMOVED name lists (the audit trail survives even when the flow replaces itself and the final toast is lost).
- **Restore** (two clicks): reads `wp-backup-latest.json` from disk (works after a Node-RED restart), inspects it (flow version, key count, timestamp) and asks for confirmation. On confirm it first writes a safety copy of the current state (`wp-prerestore-snapshot-<timestamp>.json`), then restores every settings key. The restore itself is therefore reversible too.
- **Admin login**: dashboard fields (password masked) or, safer, the `WPU_ADMIN_USER` / `WPU_ADMIN_PASS` environment variables of the Node-RED container: the password then never sits in the editor or context. UI fields win over env vars. Since v4.8 nothing credential-like is persisted: the UI password and both tokens (admin bearer, download) live only in the memory store. The Admin API URL is **not** a dashboard field anymore: it is derived server-side (loopback `http://127.0.0.1:1880`, or the `WPU_ADMIN_BASE` env var), so someone with dashboard-only access cannot redirect credential POSTs to an external host. Note: a Node-RED function node cannot read `httpAdminRoot` from settings.js (the function sandbox has no `RED.settings`), so on a non-standard port or with `httpAdminRoot` set you must provide `WPU_ADMIN_BASE` yourself.
- **Update flow**: downloads the new flow.json (URL pinned to the HeishaMoNR repo), fetches the palette (`GET /nodes` with `Accept: application/json`), refuses on missing node types, writes a pre-update flow snapshot first (rollback next to the rev conflict check), then runs the id-based merge and deploys everything in one atomic operation (`POST /flows` with rev conflict check). Since v4.9 the deploy reports **what changed**: the toast states how many nodes are new (with the names), updated, removed and unchanged, and the full per-node lists go to the Node-RED log, so "which nodes were updated" is answerable afterwards. A version check older than one hour is refused; an expired admin token (401) is refreshed automatically, and refreshed proactively after an hour. Before merging, the download is verified: the changelog node inside the file must report the expected version (wrong file or forgotten bump = refuse, nothing changed).

## What Ed can put in the repo (optional)

Without a version pointer the tab already works via the repo scan. Cleaner (and CI-automatable) is a `version.json` in the repo root, updated per release:

```json
{
  "version": "26.5.1",
  "flowUrl": "https://raw.githubusercontent.com/edterbak/HeishaMoNR/main/flows (26.5.1 stable).json",
  "notes": "Fixed bug #218; RTC revert fix"
}
```

The tab tries `version.json` first; if absent, the repo scan follows; only if both fail (GitHub unreachable) does a clear error appear and nothing changes. Optionally on top: GitHub releases, so `update_instructions.md` can refer to them.

## Install (one-time)

0. If an earlier version (v3/v4.0) is already imported: delete that tab completely first (select tab > Delete; then Configuration Nodes > unused, remove the old WP Update `ui_tab`/`ui_group`) before importing the new JSON; node ids are unchanged, so double ids would clash.
1. Import `update-tab.json` (menu > Import). A **WP Update** flow tab and an **Update** dashboard tab appear. The deploy shows no warnings: the file nodes and toast conform to the palette definitions (DB1).
2. In the dashboard, optionally set **Admin user/password** (only if the editor is protected with adminAuth; the token is fetched via `POST /auth/token` and kept session-only in memory). There is no Admin API URL field anymore (v4.8): the tab derives it server-side as `http://127.0.0.1:1880`, unless you set the `WPU_ADMIN_BASE` environment variable (required for a non-standard port or a non-empty `httpAdminRoot`, since a function node cannot read settings.js). Set **Backup directory** to `/data` if Node-RED runs in a Docker container, so backups and snapshots survive container recreation.
2b. (v4.11+) No further imports needed: **Check for updates** also refreshes the **Tab status** field (one click, both checks); **Update tab** then keeps this tab itself current from this repo.
3. Press **Check for updates**. If Available shows "26.5.1 (update!)": **Back up settings**, then **Update flow**. (The same click also refreshes the Tab status field.)
4. After the deploy the flows restart: refresh the dashboard and check the new version on [WP Home].

## Manual restore of a local backup (worst case)

The browser download from [Back up settings] is not a convenience extra: it is the disaster-recovery copy. The on-disk backup (in the Node-RED data directory) and [Restore backup] only exist while Node-RED én this tab still work. If the tab or the whole update chain is ever broken, the file you downloaded to your own PC is the artifact you restore from: [Back up settings] before every risky change, and click the download link in the toast so the copy actually lands on your PC.

When that moment comes, [restore-helper.json](restore-helper.json) is the no-SSH, no-dashboard path:

1. Node-RED runs, the tab does not (or you want to restore without it): import `restore-helper.json` (menu > Import) and Deploy. It adds one small flow tab "WP Restore helper (delete after use)".
2. From the PC that has the download, POST the file to the helper:

   ```bash
   curl -X POST -H "Content-Type: application/json" \
     --data-binary "@wp-backup-2026-11-22-18-54-49.json" \
     http://<node-red-host>:1880/wpupdate/restore-helper
   ```

   Default Node-RED settings accept POST bodies up to `apiMaxLength` on http-in nodes (default 5 MB; verified in the 5.0.10 `21-httpin.js` source), settings backups normally fit.
3. The response states how many settings keys were restored and from which backup moment. Restore semantics are identical to the tab's own [Restore backup]: every key in the backup overwrites the current value, keys that exist now but not in the backup stay, `WPU_` state is never restored.
4. Check the WP dashboard ([WP Home]) and the critical settings (trigger/revert values), and let the WP flow restart if needed.
5. DELETE the helper flow again: it listens on the LAN without authentication (http nodes sit outside adminAuth). Import, use, delete.

The helper uses `wprh`-prefixed ids on purpose and never touches `wpu` ids, so it cannot collide with the [WP Update] tab in any state.

## Merge rules of the core

1. Nodes inside package tabs (tab/subflow ids are stable across versions, verified 26.3.1 -> 26.5.1): replace the local definition with the new one. Safety net for a fully rebuilt release (all-new ids): flow tabs are additionally matched on their stable labels (the 10 package tab names have been identical in every release so far), per label only when no local tab with that label matches on id; old package tabs are then still cleaned up, and a personal tab that coincidentally carries the same label is guaranteed to survive an id-stable release.
2. Broker rescue: if the new package references an unconfigured placeholder broker (host "x.x.x.x") that does not exist locally, all package mqtt references are rewritten to the locally most-used broker. Prevents the heat pump silently dying on a broken MQTT config after a rebuild.
3. Package config nodes by id: same, except `mqtt-broker`: the **local broker always wins** (your host/port stays untouched).
4. Broker references inside package mqtt nodes keep the **local** broker (works for the package placeholder config and for a fully own broker).
5. Everything outside the package (personal tabs, own dashboard items, own brokers, other integrations): untouched.
6. Singleton configs (`global-config`, `ui_base`): only the package version survives (prevents duplicate manifests with per-release changing ids), but the env array of the local `global-config` is merged: your own environment variables win, new package entries are added.
7. Pre-flight: palette check (`GET /nodes` with `Accept: application/json`; only sets without err and with enabled=true count; tab/subflow/group/junction and subflow instances are flow-config types, not palette types) and duplicate-id check before the POST. After passing, the current flows are first written to a pre-update snapshot.
8. Reporting instead of blind deletion: old ui_tab names are partly generic ("Home", "Settings"), so old dashboard tabs are never silently dropped but reported on the result screen; same for local tabs with a WP name the new package does not know. An own ui_tab with a generic name like "Home" is guaranteed to survive. The ui_tab warning only sounds on a genuinely detected id-rebuild (label match without id match), not on an id-stable update.
9. The POST is atomic with a rev conflict check (409 = flows changed in between, press again). On a failing merge or POST nothing changes and the old version keeps running.
10. Download URLs from `version.json` are pinned to `https://raw.githubusercontent.com/edterbak/HeishaMoNR/...`; a tampered `version.json` therefore cannot make the tab download arbitrary URLs.

## Honest edge cases

- Hand edits *inside* [WP ...] tabs are reset to package defaults (same as the official procedure; the backup covers settings, but own code inside package tabs belongs in [WP Personal] or upstream as a PR).
- Own nodes placed *inside* a WP tab (against the project convention) fall under the tab swap and disappear. Keep personal stuff in [WP Personal].
- Since v4.8 nothing credential-like is persisted: the UI password, the admin bearer token and the download token live only in the memory context store (gone after a restart — re-enter the UI password or use the env vars, which remain the persistent route). The Admin API URL is never taken from the dashboard, so `WPU_ADMIN_USER`/`WPU_ADMIN_PASS` cannot be exfiltrated to an arbitrary host by someone with dashboard-only access. Caveat: the "memory" store only exists if settings.js defines it, or if no `contextStorage` block is configured at all (then memory is the default). If your settings.js defines a `contextStorage` whose default is a file store and no explicit `memory: { module: "memory" }` store, Node-RED silently falls back to the default store and the password/token land on disk. Fix: add an explicit memory store:
  ```js
  contextStorage: {
      default: "file",
      memory: { module: "memory" }, // the tab's credential store
      file:   { module: "localfilesystem" }
  }
  ```
- Backup and snapshot files (`wp-backup-*.json`, `wp-prerestore-*.json`, `wp-preupdate-flows-*.json`) are plain JSON containing the full global context / full flows — keep the Node-RED data directory (and the optional Backup directory) readable only by the Node-RED user.
- After a successful deploy the final toast may no longer appear (the flow replaces itself); the version on [WP Home] is the real confirmation.
- GUI_01/GUI_02 disabled tabs and the changelog node are recognized and covered in the tests.
- The backup covers the default global context store; settings in a named store stay outside (HeishaMoNR uses only the default store).
- Restore is a JSON round-trip: Date/Buffer/Map values come back as plain JSON (strings/arrays). In this package (settings and numeric history) that plays no role.
- `http in` routes sit outside adminAuth; the download endpoint therefore works only with a one-time token. If your Node-RED port is not on a trusted LAN only, set `httpNodeAuth` in settings.js.
- Admin tokens expire (default after 7 days): the tab catches the 401, clears the token and fetches a new one on the next click; after an hour the token is refreshed proactively.
- A successful deploy is no proof that the new flow is healthy at runtime. If the new version fails to start, import the latest pre-update flow snapshot (`wp-preupdate-flows-<timestamp>.json`) in the editor; the settings backup covers the global context.
- The settings backup covers only the default global context: no node/flow context, no config-node credentials (those live encrypted in the flows), no external files/databases. For HeishaMoNR (settings + history in the global context) that suffices; it is not a complete Node-RED backup.
- The repo scan reads the HTML of the repo root page. Live checked: the root has 9 files and the HTML payload (234 KB) contains all flow-json names in full; the scan finds 26.5.1. GitHub lazy-loads the file list only on much larger repos; if the root ever counts dozens of files the scan could become incomplete. That is why the scan is deliberately a "fallback": `version.json` in the repo is the recommended primary route.
- If Ed ships this tab inside the package release, it self-updates cleanly on id-stable releases. Only a locally renamed copy with different node ids remains as a duplicate tab and needs a one-time manual cleanup.

## Feature request / draft PR: self-service update tab

The full FR text as filed with HeishaMoNR:

> The current update procedure (manual tab deletion, config cleanup, screenshots for settings) is error-prone and costs every user 30+ minutes per release. Since node ids are already stable across releases (verified: 26.3.1 -> 26.5.1 share 3547 ids; 1 removed, 15 added), a scripted atomic update is safe. This tab ships inside the flow package and reduces every future update to: Check for updates, Back up settings (full global context to a timestamped file plus a fixed latest copy, downloadable via /wpupdate/backup), Restore backup (two-click restore from disk that works even after a Node-RED restart, and writes a pre-restore snapshot of the current state so the restore itself is reversible), Update flow (id-based atomic merge via the Admin API with palette pre-flight and rev conflict detection; local mqtt-broker config and all personal tabs are preserved by design). Admin credentials can come from environment variables (WPU_ADMIN_USER / WPU_ADMIN_PASS) instead of the dashboard fields, so no password needs to sit in the editor or context.
>
> The tab ships with a repo-scan fallback (reads the plain repo page, picks the highest "flows (X stable).json", no GitHub API, so no rate limits) and therefore works with the repo as it is today. It is also robust against a fully rebuilt release (all-new node ids, which the repo has not done so far but could): flow tabs are additionally matched on their stable labels, placeholder MQTT broker references are rescued to the locally most-used broker, and leftover old dashboard items are reported rather than silently deleted. Recommended addition: a `version.json` in the root, updated per release (generation can be automated in CI): `{ "version": "...", "flowUrl": "https://raw.githubusercontent.com/.../flows (X stable).json", "notes": "..." }`
>
> The pre-flight reads GET /nodes with Accept: application/json (required by the editor API) and only counts enabled, error-free node sets; tab/group/junction/subflow instances are flow-config types, not palette types. Before every deploy the current flows are written to a pre-update snapshot (wp-preupdate-flows-<timestamp>.json) as a rollback next to the rev conflict check. Backups go to an optional backup directory (/data in Docker) and the download endpoint requires a one-time token from the toast, because http nodes are not covered by adminAuth. Download URLs from version.json are pinned to the repo, releases are X.Y.Z only, and before merging the changelog node inside the downloaded flow must report the expected version (wrong file or forgotten bump = refused, nothing changed). Download tokens expire after 24 hours; admin tokens are refreshed hourly. The tab-swap by label only applies when no local tab with that label matches on id (a personal tab coincidentally named like a package tab survives an id-stable release). A successful deploy covers the deploy operation; the pre-update flow snapshots are the recovery path if the new flows fail at startup. If this tab ships inside the package itself, an id-stable release self-updates it cleanly; a locally renamed copy with different ids would remain as a duplicate tab and needs a one-time manual cleanup. The tab follows the existing in-flow Admin API precedent (GUI_01/GUI_02 tab-toggle already uses PUT /flow/:id). Full merge rules, test report against the real 26.3.1/26.5.1 packages and the importable flow JSON are in the PR.
